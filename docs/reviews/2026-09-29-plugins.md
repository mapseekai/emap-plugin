## 结论

审查确认的 3 项问题现已修复：PostGIS Node 网关取消清理挂起（P1）、浏览器流式 token 等待无法取消（P2）、根批量脚本 Windows 路径判断（P2）。GDAL 插件本次没有确认需要修复的运行时缺陷。

## P1：取消游标查询后清理挂起，并发名额无法释放

位置：[gateway.ts](../../repos/emap-postgis-plugin/src/server/gateway.ts)，`read()` 第 42–43 行、`collect()` 第 110 行；`streamWkb()` 第 164 行存在相同的清理模式。

触发：Node 网关正在 `cursor.read()` 时，调用方取消、HTTP 断连、网关卸载或任务超时。`read()` 的 abort 回调先调用 `client.release(true)` 销毁连接；`cursor.read()` 随后拒绝，但 `finally` 又等待这个连接上的 `cursor.close()`，后者无法完成。

在隔离 PostGIS 3.6.1 数据库中，通过一个调用 `pg_sleep(4)` 的普通测试函数复现真实在途查询；不是延迟 fetch 的模拟：

```text
cursor read start
cursor read rejected
cursor close start
500 ms 后：查询 Promise 仍 pending
超过 6000 ms 网关超时后：仍 pending
maxConcurrent=1 时再调用 testConnection：BUSY
```

`read()` 的 `finally` 因此无法执行，`active.delete(task)` 不会发生。默认并发为 8，重复取消可能逐步耗尽所有名额。普通查询与 WKB 查询共用 `collect()`；流式入口也应一起检查。另观测到断开客户端连接后数据库查询仍短暂保持 active，因此关闭 socket 也不能作为服务端即时取消的证据。

建议：统一处理客户端已销毁时的游标清理，保证操作 Promise 有界结束、并发名额总能释放；数据库取消应单独验证。回归至少覆盖 `query`、`queryWkb`、`streamWkb` 在 cursor 读取阶段取消，以及取消后下一次请求成功。

现有 PostGIS 浏览器取消测试是在网关查询前加入传输延迟，不会进入这个 cursor 清理路径。连接器 Rust 原生后端的取消测试通过，但不覆盖此 Node 实现。

## P2：流式 token 等待不受超时和取消控制

位置：[stream.ts](../../repos/emap-postgis-plugin/src/stream.ts) 第 25–28 行。

`readWkbStream()` 直接 `await options.token()`，之后才开始使用 `timed()`。当异步 token 获取或刷新不返回时，配置的请求超时、调用方 AbortSignal、客户端 `dispose()` 都不能结束该等待。

通过公开 `createPostgisClient()` 复现：配置 `timeoutMs: 10`，token 返回一个受控 Promise。30 ms 后仍 pending；调用 `dispose()` 并再等 30 ms，仍 pending；手动 resolve token 后才抛出 `AbortError`。对应的转换并发名额也会一直被占用。

建议：让 token 获取进入同一个可取消、有限时的等待过程，保持与普通 `request()` 的行为一致；验证超时、调用方取消和卸载均能及时结束。

以上两项可运行复现：

```sh
npm --prefix repos/emap-postgis-plugin run build
node test/review/cancellation.mjs
```

[复现脚本](../../test/review/cancellation.mjs) 使用既有临时 Docker 数据库 fixture，结束时清理自己创建的容器。修复前返回 exit code 1 并打印 pending / BUSY；修复后返回 exit code 0，查询以 AbortError 结束且下一次请求成功。该脚本保留为手动复现；token 回归已加入单元测试，真实数据库取消回归已加入 test:integration / verify:all。

## P2：根批量命令在 Windows 上拒绝正常插件目录

位置：[repos.mjs](../../scripts/repos.mjs) 第 10–12 行。

`resolve()` 在 Windows 上返回反斜杠路径，但代码用 `cwd.startsWith(root + '/')` 判断。有效目录也不能通过，根目录的 bootstrap/build/test/verify 会在执行插件命令前报 `Missing plugin package`。

可在任意系统确定性复现 Windows 路径语义：

```js
import { win32 as path } from 'node:path';
const root = path.resolve('C:\\workspace\\emap-plugin');
const cwd = path.resolve(root, 'repos/emap-gdal-plugin');
console.log(cwd.startsWith(root + '/')); // false
```

建议：用 `relative()` 判断目录归属或使用平台分隔符，并在 Windows 上验证后续 npm 子进程启动。当前结论验证了路径判断；没有运行 Windows 原生 shell，不能据此声称该平台其他部分已通过。

## 修复验证

- `gateway.ts`：保留每次查询独占并销毁连接的原有策略，统一由 `read()` 的释放路径清理连接、事务及游标；移除已经断开连接后无法完成的 `cursor.close()`，也不再在可能挂起的 portal 后排队等待 `ROLLBACK`。不引入额外连接池或新的取消协议。
